# Анализ результатов бенчмарка

## Условия измерений

Для оценки производительности сравнивались последовательная реализация свертки изображения и несколько параллельных реализаций:

- разбиение по строкам (`horizontal`);
- разбиение по столбцам (`vertical`);
- блочное разбиение (`block`);
- динамическое распределение по пикселям (`pixel`).

Ускорение считалось относительно последовательной реализации:

```text
speedup = T_sequential / T_parallel
```

Для каждой конфигурации выполнялось 40 независимых измерений. Перед серией измерений выполнялся прогрев. Для результатов вычислялись среднее время, стандартное отклонение и 95% доверительный интервал. Также строились гистограммы распределения времени и выполнялись тесты нормальности.

Измерения проводились по методичке: <https://github.com/spbu-se/measurements/blob/main/measurements_cheat_sheet.pdf>.

Перед финальным запуском стенд был стабилизирован:

- проект собран в режиме `Release`;
- CPU governor установлен в `performance`;
- turbo boost отключен;
- запуск выполнен с привязкой процесса к логическим CPU `0-11`.

Финальная команда запуска:

```bash
taskset -c 0-11 python3 benchmark/benchmark.py \
  --binary ./build/hw1 \
  --small testfiles/lena.bmp \
  --large testfiles/mars_large.bmp \
  --runs 40 \
  --threads 1,2,4,8 \
  --out benchmark/benchmark_results
```

Привязка к CPU `0-11` использовалась из-за того, что процессор Intel Core Ultra 7 155H является гибридным: часть ядер производительные, часть энергоэффективные. Без привязки потоков планировщик ОС мог переносить работу между разными типами ядер, что ухудшало стабильность измерений.

Важно: параметр `--threads 1,2,4,8` применялся к `horizontal`, `vertical` и `pixel`. Для блочного разбиения в скрипте отдельно использовался список `1,4,9,16`, так как число блоков должно образовывать квадратную сетку. Поэтому результат `block/16t` означает 16 программных потоков внутри ограничения `taskset -c 0-11`, а не 16 физических производительных ядер.

Дополнительно измерялась пайплайн-реализация, разделяющая чтение, обработку и запись на отдельные стадии. Параметры пайплайна:

- `w` — количество воркеров (изображений, обрабатываемых параллельно);
- `t` — число потоков обработки внутри каждого воркера.

Ускорение пайплайна считалось относительно базовой конфигурации `w=1/t=1` (последовательная обработка батча без параллелизма):

```text
speedup = T(w=1,t=1) / T(w,t)
```

Малый батч: 12 изображений `lena.bmp` (~512×512). Большой батч: 8 изображений `mars_large.bmp` (5824×4737). Для малого батча выполнялось 40 измерений, для большого — 10.

## Результаты на большом изображении

В качестве большого изображения использовался файл `testfiles/mars_large.bmp` размером `5824 x 4737`.

Последовательная реализация:

```text
sequential: 1096.6 ± 22.7 ms
```

Разбиение по строкам:

```text
horizontal/1t   1084.5 ± 2.2 ms    speedup 1.01x
horizontal/2t    574.9 ± 4.1 ms    speedup 1.91x
horizontal/4t    321.0 ± 1.8 ms    speedup 3.42x
horizontal/8t    261.6 ± 6.2 ms    speedup 4.19x
```

Разбиение по столбцам:

```text
vertical/1t     1085.0 ± 2.9 ms    speedup 1.01x
vertical/2t      575.8 ± 2.8 ms    speedup 1.90x
vertical/4t      321.6 ± 2.8 ms    speedup 3.41x
vertical/8t      264.5 ± 7.3 ms    speedup 4.15x
```

Блочное разбиение:

```text
block/1t        1084.6 ± 2.7 ms    speedup 1.01x
block/4t         321.4 ± 2.9 ms    speedup 3.41x
block/9t         247.4 ± 7.6 ms    speedup 4.43x
block/16t        247.7 ± 5.7 ms    speedup 4.43x
```

Динамическое распределение по пикселям:

```text
pixel/1t        1309.7 ± 2.8 ms    speedup 0.84x
pixel/2t        3240.6 ± 476.8 ms  speedup 0.34x
pixel/4t        2319.4 ± 102.0 ms  speedup 0.47x
pixel/8t        1700.0 ± 48.1 ms   speedup 0.65x
```

## Сравнение способов разбиения

Разбиение по строкам и разбиение по столбцам показали почти одинаковую производительность. На 2 потоках ускорение близко к идеальному:

```text
horizontal/2t: 1.91x
vertical/2t:   1.90x
```

На 4 потоках обе реализации также дают почти одинаковый результат:

```text
horizontal/4t: 3.42x
vertical/4t:   3.41x
```

На 8 потоках ускорение продолжает расти, но уже не линейно:

```text
horizontal/8t: 4.19x
vertical/8t:   4.15x
```

Это связано с накладными расходами на создание и синхронизацию потоков, конкуренцией за кэш и пропускную способность памяти, а также тем, что при большом числе потоков несколько потоков могут делить одно физическое ядро.

Блочное разбиение оказалось наиболее эффективным на большем числе потоков:

```text
block/9t:   4.43x
block/16t:  4.43x
```

Вероятная причина в более равномерном распределении работы и хорошей локальности доступа к данным. При этом результат `block/16t` нужно интерпретировать осторожно: использовались 16 программных потоков, но процесс был ограничен логическими CPU `0-11`. На `mars_large.bmp` конфигурации `block/9t` и `block/16t` показали практически одинаковый результат, что может говорить о насыщении вычислительных ресурсов при переходе от 9 к 16 потокам.

## Анализ пиксельного распределения

Реализация `pixel` оказалась неэффективной. Даже при нескольких потоках она работает медленнее последовательной версии:

```text
pixel/1t: 0.84x
pixel/2t: 0.34x
pixel/4t: 0.47x
pixel/8t: 0.65x
```

Причина в способе распределения работы. В этой реализации каждый поток получает следующий пиксель через общий атомарный счетчик. Для большого изображения это приводит к миллионам атомарных операций и постоянной конкуренции потоков за одну общую переменную.

Из-за этого накладные расходы на синхронизацию оказываются больше выигрыша от параллельного выполнения. Поэтому стратегия `pixel` для данной задачи является неудачной.

## Качество измерений

Для основных конфигураций стандартное отклонение оказалось малым:

```text
horizontal/4t         std = 0.6%
vertical/4t           std = 0.9%
block/4t              std = 0.9%
```

Это говорит о хорошей воспроизводимости измерений.

Некоторые конфигурации имели повышенную вариативность:

```text
large sequential      std = 2.1%
large horizontal/8t   std = 2.4%
large block/9t        std = 3.1%
large block/16t       std = 2.3%
small pixel/2t        std = 8.1%
small pixel/4t        std = 5.6%
large pixel/2t        std = 14.7%
large pixel/4t        std = 4.4%
small pipeline w=8/t=1  std = 11.0%
```

Повышенное стандартное отклонение у `large sequential` (2.1%) стоит выделить отдельно: в сравнении с параллельными конфигурациями последовательная реализация оказалась менее стабильной. Это сказывается на расчётных ускорениях и должно приниматься во внимание при их интерпретации. Для `horizontal/8t`, `block/9t` и `block/16t` стандартное отклонение находится в допустимых пределах. Для `large pixel/2t` стандартное отклонение слишком большое, а гистограммы имеют несколько групп значений, поэтому этот результат нестабилен.

Предупреждения тестов нормальности встречались даже у некоторых стабильных измерений. Например, для `large sequential`, `horizontal/4t`, `vertical/2t` и `block/4t` p-value у тестов нормальности меньше 0.05, но относительное стандартное отклонение меньше 1%, а доверительные интервалы очень узкие. Это означает, что распределение измерений не идеально нормально, но сами измерения воспроизводимы. Основное внимание следует обращать на гистограммы, стандартное отклонение и доверительные интервалы.

## Результаты пайплайна на малом батче

Малый батч: 12 изображений `lena.bmp`. Базовое время `w=1/t=1` = 118.7 мс.

Избранные конфигурации:

```text
w=1/t=1    118.7 ± 0.4 ms    speedup 1.00x  (baseline)
w=1/t=4     31.7 ± 0.3 ms    speedup 3.74x
w=1/t=8     29.5 ± 0.8 ms    speedup 4.02x
w=2/t=4     26.3 ± 1.2 ms    speedup 4.51x
w=2/t=8     22.4 ± 0.4 ms    speedup 5.30x
w=4/t=4     22.1 ± 0.3 ms    speedup 5.36x  (лучший)
w=4/t=8     22.3 ± 0.3 ms    speedup 5.33x
w=8/t=4     22.2 ± 0.3 ms    speedup 5.35x
w=8/t=8     22.7 ± 0.3 ms    speedup 5.23x
```

Насыщение достигается при `w=4`: дальнейшее увеличение числа воркеров не даёт прироста. Лучший результат — `w=4/t=4` при 22.1 мс, ускорение 5.36x.

## Результаты пайплайна на большом батче

Большой батч: 8 изображений `mars_large.bmp`. Базовое время `w=1/t=1` = 8321.9 мс.

Избранные конфигурации:

```text
w=1/t=1    8321.9 ± 11.4 ms   speedup 1.00x  (baseline)
w=1/t=4    2158.1 ± 22.0 ms   speedup 3.86x
w=1/t=8    1667.9 ± 10.6 ms   speedup 4.99x
w=2/t=8    1489.1 ± 16.9 ms   speedup 5.59x
w=4/t=4    1482.5 ± 12.8 ms   speedup 5.61x
w=4/t=8    1462.9 ± 9.2 ms    speedup 5.69x  (лучший)
w=8/t=4    1491.0 ± 11.8 ms   speedup 5.58x

```

Лучший результат — `w=4/t=8` при 1462.9 мс, ускорение 5.69x.

## Сравнение пайплайна с параллельными реализациями

Пайплайн обрабатывает батч изображений. Чтобы оценить его прирост, нужно сравнить с альтернативой: обработкой каждого изображения по очереди с использованием лучшей параллельной реализации.

**Большой батч (8 изображений):**

Лучший параллельный результат для одного большого изображения — `horizontal/8t` ≈ 261.6 мс. При последовательной обработке 8 изображений по одному с 8 потоками:

```text
8 × 261.6 мс = 2092.8 мс
```

Пайплайн `w=4/t=8` = 1462.9 мс. Прирост от пайплайна:

```text
2092.8 / 1462.9 ≈ 1.43x
```

Пайплайн даёт около 43% прироста за счёт того, что чтение следующего изображения и запись предыдущего совмещаются с вычислением текущего.

Для сравнения, конфигурация `w=1/t=8` (один воркер, без параллельной обработки нескольких изображений) даёт 1667.9 мс — хуже на 14%, чем `w=4/t=8`. Это показывает, что именно пересечение стадий между разными изображениями обеспечивает основной выигрыш пайплайна.

**Малый батч (12 изображений):**

Лучший параллельный результат для одного малого изображения — `block/16t` ≈ 2.1 мс. При последовательной обработке 12 изображений:

```text
12 × 2.1 мс = 25.8 мс
```

Пайплайн `w=4/t=4` = 22.1 мс. Прирост:

```text
25.8 / 22.1 ≈ 1.16x
```

Эффект на малом батче меньше, чем на большом. Причина: при небольших изображениях операции чтения и записи занимают меньшую долю общего времени, поэтому их перекрытие с вычислением даёт меньший выигрыш. Накладные расходы на управление очередью и синхронизацию воркеров становятся сопоставимы с самим выигрышем.

## Вывод

Параллельные реализации на основе разбиения изображения на строки, столбцы и блоки дают заметное ускорение относительно последовательной версии.

На большом изображении лучшие результаты:

```text
horizontal/8t: 4.19x
vertical/8t:   4.15x
block/9t:      4.43x
block/16t:     4.43x
```

Наиболее удачной стратегией оказалось блочное разбиение. Разбиения по строкам и столбцам также показали хорошие и близкие результаты.

Пиксельное динамическое распределение оказалось неэффективным из-за больших накладных расходов на атомарные операции. Его можно рассматривать как пример неудачной схемы распараллеливания.

Пайплайн-реализация, разделяющая чтение, обработку и запись на стадии, даёт дополнительный прирост около 16–43% поверх лучшей параллельной реализации за счёт совмещения I/O и вычислений. Эффект значительнее на крупных изображениях, где I/O составляет ощутимую долю времени. Насыщение по числу воркеров наступает при `w=4`: дальше планировщик уже не успевает загружать новые изображения быстрее, чем они обрабатываются.

Для отчета следует использовать результаты из папки:

```text
benchmark/benchmark_results
```

В этой папке находятся финальные CSV-таблицы, график ускорения и гистограммы, соответствующие запуску на `mars_large.bmp`.
